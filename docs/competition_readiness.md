# تقرير جاهزية عرض CORTEX-GUARD

## الحالة الحالية

النواة الخلفية وسيناريو الديمو قابلان للتشغيل والاختبار. اجتازت مجموعة الاختبارات الحالية 19 اختبارًا، بما فيها اختبار تكامل API وتسلسل الأحداث. كما تم التحقق من صفحات الديمو عبر خادم Uvicorn محلي وطلبات HTTP حقيقية. لم يتم بعد اعتماد تحميل الإضافة وإشعاراتها يدويًا في Chrome على جهاز العرض.

## ما تم إنجازه

- مراحل Backend من Normalizer حتى Pipeline وAPI موجودة.
- Manifest V3 وcontent script وbackground worker موجودة.
- الاتصال محلي إلى `localhost:8000`، والجلسات مرتبطة بمعرّف التبويب.
- سيناريو demo يمر عبر message ثم link ثم otp_request ويعيد evidence chain.
- صفحات ديمو محلية ثابتة موجودة في `demo/pages/`، واختُبرت نصوصها ضد الـAPI.
- شعار SVG/PNG موحد ظاهر في README وأيقونات الإضافة.
- badge يعرض درجة الخطر، والإشعار يعرض label والسياق والأدلة عند تجاوز الحد.
- ملفات Python وJavaScript والاختبارات مفصولة حسب المسؤولية.

## ما يجب إنجازه قبل العرض

1. إنشاء بيئة Python على جهاز العرض وتثبيت `requirements.txt`.
2. تشغيل backend ثم تحميل مجلد `extension/` عبر Chrome Load unpacked.
3. تجربة الصفحات الثلاث يدويًا في التبويب نفسه والتأكد من badge والإشعار واسترجاع الجلسة.
4. التحقق من أن الإشعار يظهر في نظام التشغيل المستخدم في المسابقة، وأن الأيقونة تظهر كما ينبغي.
5. تحميل صفحات `demo/pages/` بالتتابع في تبويب Chrome واحد، والتدرب على النقر بعد كل انتقال.
6. مراجعة الملفات وقرار الترخيص، ثم إضافة الملفات وإنشاء commit وربط remote قبل رفع المشروع إلى GitHub. المستودع المحلي مهيأ بالفعل.

## قرارات تحتاج تثبيتًا

- لا تحدد المواصفة وزن `file_risk`. يستخدم التنفيذ الحالي `0.1` مؤقتًا، ويجب اعتماده أو تغييره بقرار موثق.
- Context Engine يعيد `0.6` عند اكتشاف النمط، بينما Fusion يزيد وزن السياق فقط إذا تجاوز `0.7`. لذلك قاعدة التكيف هذه لا تعمل في المسار الحالي.
- المواصفة تسمح بالـ badge وإشعارات Chrome وتمنع النوافذ المعقدة. العرض الحالي يلتزم بذلك؛ لا توجد نافذة نتائج تعرض كل الاستجابات.

## قياس النتائج

نتيجة السيناريو التجريبي الحالية:

```text
risk_score: 0.6167
label: phishing
context_pattern: multi_step_attack
evidence_chain: urgency, suspicious URL, OTP, multi-step pattern
```

تم التحقق من صفحات الديمو المحلية عبر خادم Uvicorn وطلبات HTTP فعلية، ثم أُوقف الخادم بعد الاختبار. عند اختبار صفحة OTP تحتوي طلب الرمز فقط، ظهر `multi_step_attack` لكن بقيت الدرجة `0.2727` والوسم `safe`؛ خصائص المخاطر تُحسب من الصفحة الحالية ولا تتراكم عبر أحداث الجلسة، بينما يتتبع السياق التسلسل. لذلك تتضمن صفحة OTP الجاهزة للديمو إشارات واضحة مثل الاستعجال والرابط المشبوه والتهديد كي يطابق الخرج المثبت.

هذه نتيجة مسار تجريبي محدد وليست قياسًا للدقة. لا توجد مجموعة بيانات أو نتائج precision/recall. يجب وصف النظام في العرض كـ MVP deterministic تجريبي، دون ادعاء دقة عامة.

## GitHub والتعديل لاحقًا

README الجذر و`.gitignore` جاهزان، ومستودع Git المحلي مهيأ. الملفات غير مضافة بعد، ولم يُنشأ commit أو remote ولم يتم أي رفع. راجع `git status` واختر الملفات والـ license قبل الرفع. بنية الخدمات والاختبارات المنفصلة تساعد على طلب تعديلات مستقبلية من مساعد برمجي على ملف أو مرحلة محددة.
